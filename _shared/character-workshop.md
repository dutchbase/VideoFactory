# Character workshop

Follow the current session and named-character permission in [`permissions.md`](permissions.md). Stage completion, human review and paid generation approval are separate.

Create a character from a prompt. No character records ship with VideoFactory: you make your own with the character factory (`_templates/character-factory/`). For new discovery, a real agent opens a tailored question form (Brainstormform) and saves its URL and complete Finish result (typed answers, notes, submitted time, skipped, unanswered and hidden fields) with the current `expected_revision` at `PUT /api/creative/character/<id>/answers`. Edit the brief before its gate. The editable `character.md` profile covers identity intent, personality, appearance, clothing, references, voice and relationships. Exact human-approved appearance constraints live in `reference-set.json`, avoiding duplicate master facts. Brief, design, identity and each `animation:<variant>:<action>` use fingerprinted human review when required by current permission or requested by the user. File presence is not approval.

After the brief gate, prepare an OpenAI `character-concepts` batch for exactly three distinct images. Before any paid image generation, show the exact managed request and known cost and get separate quote approval. Stop if cost is unknown or native billing is unbounded. Run the approved batch through `studio.generation`; register only completed validated outputs with `studio.characters.register_character_candidates`. Select exactly one candidate before design readiness. Selection changes the design fingerprint. `candidates.json` is a generated registry, not a `/api/files` editing surface.

If you change the brief after its human approval, complete a fresh three-image batch, then use Studio's explicit candidate replacement check. Registration requires the current brief fingerprint, `confirm_replace: true`, and `replace_revision` equal to the current `candidate_revision` from character detail. It archives the prior registry and leaves old generated art, review events and installed video snapshots intact. The new concepts need a new selection and design gate.

After the design gate, `prepare_character_identity` attaches the selected concept as a material reference and prepares the two-image sheet/in-scene batch. Before paid generation, use the exact managed quote approval above. When both validated images exist, `register_character_identity` records their hashes, selected concept hash, explicit appearance constraints and front/three-quarter-right views. `reference-set.json` is written only by that registration route. Human approval of identity is separate from generation batch approval.

If you change the selected concept and complete the design gate, complete a fresh identity batch bound to that selection. Studio's explicit identity replacement check sends `confirm_replace: true` and the current `reference_revision`; stale revisions fail. A current `changes-requested` identity still supports the existing refinement call. Replacing either record leaves the former generated images and review history available; the new identity needs human review when required by the current permission. An existing style variant can likewise be refreshed from a current completed batch with explicit confirmation and its `variant_revision`; its actions need fresh review/export against the new art when required by the current permission.

After the identity gate, `prepare_character_variant(root, id, variant, style_id, prompt, monochrome_exception=False)` attaches both sheet and in-scene material references to an OpenAI batch. The batch captures `context: {variant_id, style_id, style_revision, monochrome_exception}`; `style_revision` is `ws._style_revision(root, style_id)` over the current style recipe, materials and template files. A changed style blocks batch run or registration. Before paid generation, use the exact managed quote approval above. When its one image is completed, `register_character_variant` verifies that exact context and writes a draft `variant.json` with the actual artwork path/hash, approved identity revision, reference-set hash, material IDs, views and monochrome exception flag. `variant.json` is not a `/api/files` editing surface. A monochrome flag is only a draft request until the variant's action review accepts it. The next step adds `assets.json`, `rig.json`, `motions.json`, and per-action preview and frame files. It must define actual parts and crops from the verified artwork. Each action remains draft until its own human review; an agent may complete work under full permission when checks pass.

An asset part may set `size: [width, height]` in canvas pixels to scale its crop; its anchor stays measured in destination pixels, and omitting `size` keeps the crop's native dimensions.

Optional `clip` is a 3–128 point polygon of normalized `[0,1]` coordinates relative to the crop; each point maps to `[x * width - anchorX, y * height - anchorY]` and follows the part's rotation.

A rig expression may name one part ID or a list of 1–8 distinct part IDs; grouped parts show together and follow the head, while mouth and prop roles remain single-part.

Read states at `GET /api/characters/<id>` and `GET /api/creative/character/<id>/reviews/<gate>`. Ready and decision endpoints use `expected_revision` equal to the current gate fingerprint. When human review is required, open the exact returned review URL, send it to the user and wait for a decision on that revision. A saved file, agent request or completed generation never equals human approval.

# OpenAI image generation

Use `studio.generation` for authored raster art. No generation request is an approval of the resulting artwork. You first approve the current upstream creative gate, then separately approve the exact image batch. Only validated completed outputs should be put into character candidate, identity or style material review records.

## Batch contract

1. Call `prepare_generation(root, request)` with a unique lowercase `id`, `subject_type` (`style` or `character`), `subject_id`, `purpose`, prompt, `references`, `transparent`, `image_count`, `input_revision`, and chosen `transport`. `provider` can only be `openai`. Get `input_revision` from the currently approved gate fingerprint. Each reference is `{"material_id":"...","role":"what the attached image should guide"}`; the referenced material must contain readable raster files. The record freezes their file and material hashes.
2. Show the returned `review` object and `resolved_references` to the user. It states purpose, image count, prompt, route and exact source image hashes. Ask for this batch approval. `approve_generation(root, id, reviewer)` records it; it never marks creative art approved. The OpenAI API route additionally requires `billing_acknowledged=True` after its separate cost/setup choice.
3. Run the approved route once with `run_generation(root, id, transport=...)`. A stale gate or changed reference blocks the call. A current gate and unchanged references are checked again during registration. `generation_detail(root, id)` shows states `awaiting-batch-approval`, `approved`, `running`, `partial`, or `completed` and any error. An active run cannot be started twice.
4. Inspect each actual image. Register only saved raster files in the returned `output_dir`. Registration checks path confinement, symlinks, image decoding, dimensions, expected count, source hashes and genuine alpha when `transparent` is true. The result stores provider, transport, coordinating agent, reported image model or `unknown`, prompt, hashes, times, dimensions and output paths. A partial run keeps valid draft records and never implies completion.

Purpose/count/gate: `character-concepts` = three images after `brief`; `character-identity` = two after `design`; `character-variant` = one after `identity`; `style-material` = one after `brief`. For identity, exactly one entry in `01_design/candidates.json` must have `selected: true` before design review approval; the batch must attach a material image matching that selected concept. For variants, attach material images matching both the approved `reference-set.json` sheet and in-scene example. Source role belongs in the generation instruction, not in a mandatory upload taxonomy.

## Routes

`codex-cli` is the default for Claude delegation. The bridge preflights Codex installation, login, image-generation feature and `exec` image/structured-output flags without printing credentials. It invokes `codex exec` with `$imagegen`, actual `--image` reference attachments, a JSON response schema and a fixed request output directory. The JSONL trace must show a completed successful call to the exact `image_gen.imagegen` tool; claimed paths or text mentioning the tool cannot complete the request. CLI and API outputs can only be registered by their active runner, never through public `register_generated_outputs`. Codex's `--model` is a coordinating language model setting, never evidence of the underlying image model. The bridge records the image model as `unknown` unless the transport itself reports it. This live CLI path requires a real authenticated Codex image tool in that subprocess.

`native` is an agent-owned handoff. `run_generation(..., transport='native')` returns instructions; it does not pretend a background image service is running. The agent calls the built-in OpenAI image tool, copies each tool-produced image byte-for-byte into `output_dir`, and calls `register_generated_outputs(root, id, [relative_paths], provenance)`. Provenance must include `provider:'openai'`, `transport:'native'`, a nonempty `coordinator`, `image_tool_used:true`, and `tool_results`: one actual `{image_url:'data:image/...;base64,...'}` result per file. Registration hashes the decoded tool image and checks it equals the saved file. Use one call per requested asset; do not invent success or silently change routes.

Native output HTTP registration has a separate 65 MiB JSON request cap for at most three approved images. Each saved/decoded image is capped at 16 MiB and 4096×4096 pixels. Ordinary Studio JSON edits retain the 2 MiB cap. Oversized registrations fail before changing batch outputs.

Studio offers `native`, `codex-cli` and `openai-api` when preparing each character concept, identity, variant or animation-art batch. Studio defaults to `native` for an active Codex agent; Claude delegation should explicitly choose `codex-cli`. The API choice requires an explicit image-model selection in Studio and a separate billing acknowledgement at batch approval. Transparent variant and animation art requires the explicit `gpt-image-1.5` choice. The saved batch route/model are immutable through execution; a different route needs a new batch and your review.

`openai-api` is an explicit paid fallback. Select it in the batch, acknowledge billing when approving, configure `OPENAI_API_KEY` locally, and use the installed official `imagegen/scripts/image_gen.py` through the bridge. The default API model is `gpt-image-2`. True API transparency requires explicitly selecting `image_model:'gpt-image-1.5'` in the reviewed batch; no automatic model downgrade occurs. Reference images are passed to the official script's edit command. The bridge does not modify that installed skill. A failed or timed-out call leaves the batch incomplete; inspect its output directory before deciding whether to prepare a fresh batch.

No route automatically retries, approves artwork or publishes. The local Studio has guarded `/api/generations` prepare/list/detail, approve, run and native output registration routes. Its batch page displays the exact record before approval and keeps partial outputs visible. A native run returns an agent handoff; it never starts a background image service.
